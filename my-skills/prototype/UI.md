# UI Prototype

用可运行的界面变体回答“哪种布局、信息层级或交互更合适”。每个变体都要改变结构或主要操作，不能只换颜色或文案。原型统一遵守主文件的分支、提交、三态确认和独立实施规则：[SKILL.md](SKILL.md)。

## 适用形态

- 页面已经存在，或自然属于某个现有页面：优先在原型分支中接入该页面，在同一路由比较变体；保留有助于判断的真实外壳、数据密度和上下文。
- 确实没有合适的现有页面：最后才在原型分支内建立明显标记为 prototype 的临时页面，并说明为什么不能嵌入现有页面。
- 默认准备 3 个变体，最多 5 个。用户已限定数量时遵循用户范围。

## 制作

1. 写明正在回答的设计问题、要比较的方案和每个方案的假设。举例：“比较设置页的三种信息组织方式；A 按任务分组，B 按角色分组，C 按最近修改排序。”
2. 按项目已有技术、组件和启动方式制作变体。变体应分别探索布局、信息优先级或主要操作；避免共享一个无法改变的整体布局。若没有合适的项目运行方式，制作容易直接打开的单文件演示并写清运行方法。
3. 默认在同一路由使用 `?variant=A` 等 URL 查询参数切换变体，使选择可分享且刷新后保留；沿用项目路由器实现 URL 更新。若项目技术限制不支持查询参数，可用等效的 URL 状态机制并说明原因。保留现有页面的数据获取、参数和认证流程，只切换呈现子树。变体名称、当前选择和关键业务状态应清楚可见。
4. 读取真实数据只在用户授权且确有助于比较时使用；交互写入默认作用于内存或隔离资源。不得让原型变体触发真实业务修改。
5. 按主文件要求实际运行并逐一操作变体，检查主要状态、关键操作和必要的窄屏/空数据情况。把运行命令、访问方式、观察到的差异、证据和未覆盖情况写入原型说明，并随相关原型文件提交。

## 原型切换条

在原型页面底部中央放置醒目的悬浮切换条，包含前一个变体、当前变体标识（键和名称）及后一个变体。前后箭头循环切换；切换后同步 URL 查询参数。支持键盘 `←` / `→` 切换，但焦点位于 `<input>`、`<textarea>` 或 `[contenteditable]` 时不拦截按键。切换条应与被评审的页面视觉区分，并在生产构建中隐藏，作为误合入时的保险。

按项目技术选用路由和构建方式，不绑定特定框架；若环境无法实现其中一项，采用最接近的可分享、可刷新方案，并在说明中记录差异和限制。原型分支隔离和生产构建隐藏是两层保护。

## 评审与交接

评审时展示可访问的原型、切换方式、问题、各方案差异和实际观察；指出当前推荐项，但不替用户下结论。列明所示原型 `branch@commit`、拟实施范围和运行证据；用户尚未答复时注明“用户结论：待确认”，并请求用户明确选择“通过并进入实施 / 退回 / 暂缓”。将结论、方案和范围关联到实际审阅的原型版本。

“喜欢 B”可作为偏好证据，但没有明确表达通过并进入实施时，不能开始正式实现。按主文件规则接受明确的自然语言确认，不要求固定口令。每次收到通过、退回或暂缓结论后，将日期、用户原意、所选方案、范围和被审阅的原型 SHA 追加到原型分支的设计记录，并做独立的本地归档提交；该归档提交引用先前原型 SHA，不写自身 SHA。提交受阻时如实报告归档未完成。退回时按反馈更新原型提交并重新运行受影响的操作，再请用户确认新版本；暂缓时保留原型、原型提交和结论。实质修改会使原确认失效。

只有用户明确通过并进入实施、且确认归档已提交后，才在新的 `codex/implement-*` 分支上实现选定方案。按确认范围将选定设计落实到正式页面，不整支合入原型分支，也不把原型页面、原型路由或变体切换器带入产品。实施交接链接被审阅的原型分支和 commit、确认归档分支和 commit、用户结论、选中方案、确认范围及项目检查结果；原型留存，除非用户明确要求清理。

## 避免

- 只改颜色、文案或间距，却称为结构不同的变体。
- 把所有变体强行放进共享布局，导致无法比较信息组织方式。
- 把评审偏好、静态检查或助手建议写成用户已确认。
- 让界面原型产生真实业务写入，或将原型切换控件带入正式产品。
