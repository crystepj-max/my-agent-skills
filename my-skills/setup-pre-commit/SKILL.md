# 配置 Pre-Commit 检查

用户要求配置或调整提交检查时，直接按仓库工具链完成必要的依赖和最小配置，不逐项重复询问。优先在已有机制中补齐覆盖，不为配置看起来更少而删掉检查。保留用户的暂存、未暂存和未跟踪工作；正式项目的探测提交与提交业务变更是两种不同授权。

## 1. 盘点现状

1. 确认仓库根目录、本次目标和 Git 状态；记录暂存、未暂存、未跟踪内容，避免覆盖或格式化无关工作。
2. 盘点 Git hooks 实际使用路径、现有 hook manager、hook 命令及顺序、`prepare` 脚本、包管理器和锁文件、格式与 lint 配置、项目已有的 `lint`、`typecheck`、`test` 等命令，以及 CI/review 规则。以当前文件、脚本和可取得的运行证据为准；配置文件存在不等于检查实际接线或已运行。
3. 如果已有 hook manager，就沿用其入口和命令顺序，在其中补齐缺失检查；保留已有 hook 与 `prepare` 内容，不并装第二套管理器，也不通过修改全局或仓库 `core.hooksPath` 强行接管。检查已存在但未接线、失效或覆盖不足时，记录为缺口并修复本次授权范围内的部分。

## 2. 配置检查

- 用户明确要求配置提交检查，已授权本任务必需的项目级开发依赖和最小相关配置。使用仓库实际选定的包管理器及与本地 Node 版本兼容的依赖版本；保留现有 manifest、锁文件、脚本和配置，不做全局安装或无关升级。
- 若 Node 项目没有现成 hook 机制，使用合适版本的 Husky、lint-staged 与 Prettier 完成可运行的设置，包括必要的 `prepare`、hook 入口、staged-file 规则和实际格式配置。若项目已有机制或不是 Node 项目，适配现有工具链，不强接管 `core.hooksPath`。
- 默认覆盖暂存文件的格式与适用 lint，并纳入项目已有且与提交范围相关的 typecheck、test 等检查。保留相关检查的现有强度；不能只因预计耗时就删除或跳过。若用户明确要求的能力没有现成脚本，报告缺口，并在授权范围内建立合适检查；不能把“脚本不存在”写成通过或静默放弃。
- 先用实际运行取得耗时、覆盖和副作用证据，再判断是否需要分层到 pre-commit、pre-push 或 CI。若分层，说明每项检查的触发点、覆盖范围和未覆盖处；不得悄悄把完整检查移出提交路径而留下空档。CI 只有在触发条件、目标分支和真实运行证据支持时才可计入有效覆盖；仅有 workflow 文件时标记未验证。有价值的独立重复检查可以保留。
- 有现成格式规则时沿用。若没有，按语言、编辑器约定或工具默认选择一套能工作的最小规则并说明选择，无需逐项审批；只格式化约定范围内的文件，不做无关全项目格式化。范围应排除二进制和项目不支持的文件类型。
- 合并 hook 时保留原有命令与先后顺序；`prepare` 已存在时只补入必要调用，hook 文件已存在时只做最小调整。不要运行会覆盖既有配置的初始化向导。

## 3. 验证真实提交链路

先检查 manifest 与锁文件一致、hook 入口和命令顺序、实际脚本、格式规则及受影响文件范围。帮助、dry-run、静态阅读或命令单独退出 0 只能说明配置或脚本状态，不能证明 Git 提交时 hook 生效。

在独立临时 Git 仓库和 fixture 中验证真实 `git commit` 链路；不要用 linked worktree 代替，因为它可能共享 Git 配置。隔离仓库应重现实际 hook manager 入口、命令、脚本和支持依赖，不得用无关的 shell hook 冒充 Husky 或其他 manager 链路。隔离 Git 配置、索引和临时文件；测试身份仅通过单次 Git 命令的 `-c user.name=... -c user.email=...` 等参数提供，不改用户真实身份、签名或全局配置。

至少验证以下行为，并检查相关命令确实被触发：

1. 放入不可自动修复的 lint、typecheck 或测试违规样例，运行真实提交；提交应失败，HEAD 保持不变，并从输出或独立记录确认失败检查实际运行。格式错误若由 formatter 自动修复，不应被当作漏检：它可以自动修复后提交成功。
2. 放入合法样例，确认真实提交成功且必要检查运行。
3. 若原来已有 hook，确认原 hook 仍执行且顺序保留。使用部分暂存文件和无关改动验证 formatter 只影响授权文件范围，并保护暂存内容、未暂存修改及其他文件；记录提交前后隔离 fixture 的索引与工作区状态。
4. 检查正式项目工作树与索引在验证前后未变。隔离 fixture 中的测试提交不授权暂存或提交正式项目文件。

缺少依赖、无法在隔离环境复现 manager，或平台不支持真实运行时，如实标明实际原因和未验证范围；不得用帮助、dry-run、退出 0 或 hook 文件存在宣称真实链路通过。

## 4. 交付状态

分别报告：配置是否完成及涉及的文件/依赖；独立临时仓库中的真实提交验证是否通过、哪些检查实际触发及 fixture 结果；正式项目是否发生真实提交；以及仍未验证的平台、CI 触发或执行路径。不要在正式工作树暂存文件或做探测提交。已有明确正式提交授权覆盖本次内容时可继续完成；否则保持改动供审阅，不推送或发布。
