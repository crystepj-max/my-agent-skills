# ClashX + OpenAI SSE 断流排查

当 Codex 桌面端或其他客户端出现 `stream closed before response.completed`、反复重连或 SSE 长连接中断时，按当前机器上的实际配置逐层定位。ClashX 版本、监听端口、控制 API、规则格式、网络策略和应用进程都可能变化；本 Skill 中的默认端口与历史现象只是检查起点。

## 执行边界

- 默认只读查看进程、配置、控制 API 和连接状态。命令只访问本机回环地址或用户指定的远端测试端点；不要打印、复制或写入控制 API 密钥、代理凭据、订阅 URL 或配置中的秘密。
- 规则、节点、DNS 配置、系统代理和应用设置的改变会影响连接。先指出证据与最小改动；只有用户明确要求修复且授权范围涵盖该改动时才执行。每次只改一项并验证，失败时恢复该项备份。
- 不用 `kill -9` 或批量重启作为默认排查动作。若证据指向进程状态，先说明影响，按用户已有授权选择正常退出和重启。
- 不预设 OpenAI 一定必须走代理、DNS 一定损坏、某个地区/节点一定稳定，或热重载必然导致崩溃。把这些作为假设，用当前结果验证。

## 排查顺序

1. **记录触发条件**：完整错误、发生时间、目标域名、是否仅流式请求失败、普通短请求是否成功、同一应用在其他网络下是否复现。避免复制带令牌或用户数据的请求正文。
2. **确认实际进程和端口**：读取 ClashX 当前监听端口、系统代理设置及应用自己的代理设置。`9090`（控制 API）和 `7890`（HTTP 代理）是旧配置中的默认示例，不应直接假定当前值。
3. **核对 API 是否可用**：如果当前版本提供本机控制 API，先从用户配置或客户端设置确认地址、端口及鉴权方式，再对 `/version`、`/rules`、`/proxies`、`/connections` 等当前支持的只读端点探测。端点或字段缺失时，以本机当前版本文档为准，不反复猜路径。
4. **比较连接路径**：按用户授权和当前网络约束，分别用当前配置的代理地址与系统默认路径对同一无凭据请求做短时连通性检查。只记录状态码、耗时和错误类别；不要发带业务数据的请求。`401` 仅表明某个 HTTP 服务返回了未授权响应，不证明应用鉴权或完整 SSE 正常。
5. **验证长连接**：优先复现用户原本的无副作用请求。如果没有安全的测试端点，可用公开 SSE 流短时测试（例如下方参考命令），但先确认网络测试符合用户环境要求；将“无事件窗口”与“连接断开”区分开。
6. **定位到客户端**：若代理层短连接和长连接正常，查看本机连接记录中是否出现目标客户端/域名。没有记录可能表示客户端没有经过该代理；记录存在但客户端失败，则继续检查客户端超时、连接复用、证书/系统代理设置和应用日志。

## 按证据选择修复

- **代理不可达**：确认当前代理监听地址、端口、模式和系统代理开关；更改前比较现状与期望值。
- **路由规则走错组**：只在已确认的规则中调整该域名匹配项或顺序；先备份实际配置，更新后查看规则命中结果。不要假定组名为 `🔰 选择节点` 或直接写入固定节点。
- **只有某节点长连接失败**：如用户要求切换，选择当前配置中存在的另一个候选节点，单独切换后复测同一请求。别把原始包中“IEPL 更稳定”的经验推广为普遍结论。
- **DNS 探测失败**：区分本机系统解析、代理端解析和客户端请求失败。单次 DNS HTTP 500 或超时只是证据之一；不要据此直接重载或清空 DNS。
- **配置更改没有生效**：检查当前配置来源是否由订阅或客户端管理、保存位置和生效状态。若需要重启，优先使用客户端正常退出/启动流程；不要自动修改订阅、调用热重载 API 或强杀进程。
- **只有应用失败**：确认应用实际使用的代理配置和进程状态。若确需重启应用，先保存用户工作并只退出该应用；不要根据应用名称猜测它的进程架构。

## 完成标准

报告已确认的故障层、支持判断的观察值、执行过的检查、任何改动及其回退方式，以及尚未验证的可能性。只有复现请求在相同条件下稳定通过后，才报告故障已修复；单次成功不能证明所有节点或网络都稳定。

具体只读探针、历史本机经验及其限制见 [diagnostics.md](references/diagnostics.md)。
