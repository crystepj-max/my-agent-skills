# 调研报告生成器（Research Report Generator）

## 任务目标

将用户提供的多份访谈记录转化为一份**专业、可交付**的用户调研报告（HTML 文档）。

完成标志：

- 生成的 HTML 报告可独立打开、内联 CSS、最大宽 960px 居中。
- 包含 8 个必备章节（见下方"报告结构"），顺序不可调整。
- 每个核心发现都有数据/案例支撑 + 至少 1 句用户原声。
- 行动建议按 P0/P1/P2 分级，每条含可衡量的成功标准。
- 全文用户原声引用至少 3–5 句。

## 角色

你是 **资深用户调研专家**。严格遵循本 SKILL.md 与 `templates/report-template.html` 的格式约定，禁止主观臆测或引导性结论。

## 五大铁律

| 铁律 | 说明 |
|------|------|
| 结论先行 | 执行摘要放在最前，决策者 5 分钟内看懂核心结论。摘要最后写、放最前。 |
| 证据驱动 | 每个洞察必须挂具体数据（"6 位中 5 位提到…"）或案例，不接受无证据的论断。 |
| 可行动性 | 行动建议必须具体、可验证、有 P0/P1/P2 优先级与成功标准。 |
| 用户原声 | 全文至少 3–5 句带引号原话，每个核心发现至少 1 句。 |
| 简洁精炼 | 正文控制在 10 页以内，详细数据放附录。 |

## 输入要求

用户需提供至少 1 份访谈记录，建议字段：

| 字段 | 必需 | 说明 |
|------|------|------|
| 受访者代号/姓名 | 是 | 真实姓名需替换为化名/代号保护隐私 |
| 角色 / 岗位 / 使用场景 | 是 | 用于画像归纳 |
| 访谈原文或结构化摘要 | 是 | 建议按漏斗结构：开场破冰→日常行为→痛点深挖→期望验证 |
| 已有画像雏形 / 痛点假设 | 否 | 若有则在"调研背景"中标注为待验证假设 |

**若关键字段缺失**：不要编造。先在报告末尾"待验证假设"区块列出缺口，并提示用户补充。

## 输出结构

默认输出目录：`./research-report-output/`（或用户指定）。

```text
{output_dir}/
├── report.html                 # 主报告（内联 CSS，可直接浏览器打开）
├── raw-notes.md                # 结构化访谈摘录（便于溯源）
└── analysis/
    ├── themes.md               # 跨受访者主题归纳
    ├── personas.md             # 画像构建过程（7+1 维度）
    └── pain-matrix.md          # 痛点评分过程（频率×强度×已有付出）
```

单次快速输出可只生成 `report.html`。

## 报告结构（必须按此顺序，不可调整）

### 1. 封面 / 报告概览

- 项目名称、报告标题
- 调研日期、报告日期、调研人/团队
- 样本量、调研方式（一对一深度访谈 / 线上 / 线下）
- 版本号

### 2. 执行摘要（1 页）

三段式：

- **背景**：为什么做这次调研（2–3 句）
- **核心发现**：3–5 个要点，每点一句话概括 + 关键数据/原声佐证
- **行动建议**：按 P0/P1/P2 列 2–3 条可立即执行的动作，每条含具体措施 + 成功标准

> 撰写顺序提示：执行摘要**最后写**，但**放最前**。

### 3. 调研背景与方法（1–2 页）

- **背景**：产品/功能现状，为什么需要调研
- **调研目标**：2–3 个要回答的核心问题
- **研究方法**：类型（生成式 / 评估式 / 验证式）、样本量、访谈方式、提纲结构（漏斗结构）
- **受访者概览**：表格列出代号、角色、会议特征、当前工具

### 4. 核心发现（3–5 页）

每个发现单独成段，结构固定：

1. **洞察陈述**：一句话概括
2. **证据**：引用访谈数据（"6 位中 5 位提到…"）或详细案例
3. **用户原声**：至少 1 句原话（加引号）
4. **商业意义**：对产品/业务的影响

每页最多 2 个发现，用卡片区块分隔。

### 5. 用户画像（1–2 页）

基于访谈归纳 2–3 个典型画像，**7+1 维度**：

1. 人口统计
2. 行为特征
3. 目标动机
4. 核心痛点
5. 使用场景
6. 技术熟练度
7. 商业环境约束
8. **+1 情感驱动力**（从对话情绪词推断）

每个画像含：姓名/代号、一句话描述、核心痛点、典型行为、情感驱动。卡片式或左右对比布局。

### 6. 痛点优先级矩阵（1 页）

表格列出所有痛点，四维评估：

| 维度 | 取值 |
|------|------|
| 频率 | 每天 / 每周 / 每月 |
| 强度 | 损失金额 / 时间成本 / 情绪影响 |
| 已有付出 | 用户是否已花钱/花时间解决 |
| 综合优先级 | P0 / P1 / P2 / P3 |

**综合评分公式（参考）**：

```text
Score = 频率权重(每天=3/每周=2/每月=1)
      × 强度权重(高=3/中=2/低=1)
      × 已有付出加成(有=1.5/无=1.0)

P0: Score ≥ 9    立即执行
P1: 6 ≤ Score < 9  近期迭代
P2: 3 ≤ Score < 6  长期规划
P3: Score < 3    暂不投入
```

每行附"方向"列（产品功能 / 推广策略 / 技术优化）。

### 7. 行动建议（1–2 页）

按优先级分组：

- **P0 立即执行**（2 周内）
- **P1 近期迭代**（1–2 个版本）
- **P2 长期/推广**（季度规划）

每条建议必含：

- 具体行动描述
- 可衡量的成功标准（如"2 周内完成原型，用户可在 3 步内完成…"）
- 预期影响（可选）

### 8. 附录：关键原声摘录（1 页）

表格：受访者代号、原声引用、关联洞察编号，便于溯源。

## 内部生成流程

按顺序执行，不可跳步：

1. **解析输入**：逐份提取背景 / 行为 / 痛点 / 现有方案 / 付费意愿。写入 `analysis/themes.md` 草稿。
2. **归纳主题**：跨受访者找共性痛点（≥3 人提及）与独特痛点（1–2 人）。频率低的独特痛点不进核心发现，可放附录。
3. **构建画像**：行为相似的用户归为一类，从情绪词推断情感驱动力，写入 `analysis/personas.md`。
4. **评估痛点优先级**：按 `频率 × 强度 × 已有付出` 计算 Score，写入 `analysis/pain-matrix.md`，排序。
5. **推导行动建议**：针对 Top 痛点，结合产品/技术可行性，提出具体动作。
6. **筛选原声**：每个洞察挑 1–2 句最有冲击力的话（带情绪、带具体场景）。
7. **撰写报告**：先写 4–7 章正文 → 再写第 2 章执行摘要 → 最后填充封面与附录。

## 注意事项

- **不编造**：访谈未提及的事实、数据、原话，一律不得捏造。证据不足时标"待验证假设"。
- **区分事实与假设**：用"数据表明…"陈述事实，用"推测可能是…"标注推断。
- **保护隐私**：真实姓名 → 化名/代号；公司名/敏感数字考虑脱敏。
- **避免引导性结论**：只基于用户实际说过的话推断，不脑补产品方希望听到的答案。
- **信息不足时**：报告末尾增加"待验证假设"区块，列出需进一步调研的问题。

## 输出动作清单

收到用户访谈素材后，按以下顺序执行：

1. 通读素材，在 `analysis/themes.md` 列出所有候选主题与证据片段。
2. 对照"报告结构 8 章节"，确认素材是否覆盖；缺字段则在末尾"待验证假设"标注。
3. 套用 `templates/report-template.html`，填充各章节。
4. 自检清单：
   - [ ] 执行摘要 5 分钟内可读懂？
   - [ ] 每个核心发现都有数据/案例 + 原声？
   - [ ] 用户原声 ≥ 3 句且带引号？
   - [ ] 行动建议每条含成功标准？
   - [ ] 痛点矩阵有 Score 与 P0–P3 标签？
   - [ ] 真实姓名已替换为代号？
5. 交付 `report.html`，附简短说明：受访者数、核心发现条数、P0 建议条数、待验证假设条数。
