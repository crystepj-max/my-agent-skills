# Implement Spec

将用户提供或当前项目已有的规格转化为经验证的实现。目标是交付符合规格的本地改动和清晰验证结果。Issue tracker、专用 setup 技能、提交、PR 和自动关闭工单都不是前置条件。

## 1. 建立任务图

阅读规格、验收标准、关联 ticket、仓库 `AGENTS.md` 和当前工作区状态。把工作分为：

- 已可开始、相互独立的任务；
- 必须先完成其他任务的阻塞项；
- 需求缺口或需要用户选择的决策；
- 不在本次目标内的事项。

有清楚的 acceptance criteria 时直接采用，不重复询问；若缺少会改变行为或范围的决定，先列出已能准备的部分，并只询问该决定。无法访问 issue tracker 时，以规格文本和现存文件为任务清单，不要求用户先搭建外部系统。

## 2. 安排实施

按依赖从 frontier 开始。只有当任务互不修改同一文件/资源、验证相互独立且可用容量足够时才并行。若工作区支持隔离 worktree，可以让工作者在独立环境准备小范围改动；共享主目录始终保持一个写入者。否则顺序完成，不为并行而并行。

委派前提供准确的文件、输入材料、完成条件和不允许的外部操作。集成者检查变更来源、冲突和验收标准，不把未经审阅的 worker 输出直接覆盖到工作区。

## 3. 实现和验证

逐项实现实际行为，而非只更新描述或工单状态。修复缺陷时先构造能复现用户问题的最小检查；其他变更按风险选择已有测试、lint、类型检查或手工场景。测试前读项目自己的运行命令。运行失败时区分变更错误、环境限制和已有失败，不伪称通过。

根据需要更新必要文档、迁移和配置。保留工作区中已有改动；不重置、暂存、删除或改写用户未授权的文件。若规格与仓库现实冲突，说明冲突并采用能满足目标的最小、可逆做法；只有无法安全继续的关键业务决策才暂停询问。

## 4. 集成和收尾

将完成的任务和实际验证逐一映射回规格。未完成的依赖、阻塞理由、假设和未运行检查要明确列出。需要独立审查时使用当前可用的 `code-review`，不因缺失 tracker 或外部 reviewer 而阻止本地审查。

默认只交付当前授权范围的本地文件改动与结果。可按项目约定自主选择必要、可逆的本地隔离方式（包括分支或 worktree），不要求为每项任务额外建分支。提交、推送、开/更新 PR、合并或关闭工单仍须有对应授权；准备好后提供可审阅的变更和建议动作。
