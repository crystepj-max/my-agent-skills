# Requirements Analysis（需求分析）

把一份原始输入（GitHub issue 或用户的自然语言描述）加工成「可直接执行」的需求资产。本 skill 是**编排层**：按流程调用已安装的 triage / grill-with-docs / to-tickets / wayfinder 子 skill，不重复造轮子；本 skill 的独有职责是三件事——① size 判定（triage 本身不含）、② 三要素强制产出与缺口处理、③ 落盘与 issue 回写。

## 为什么这么设计

需求从「想法」到「可执行」要跨四道坎，每道坎由对应子 skill 处理：

| 阶段 | 解决什么 | 子 skill |
|---|---|---|
| 分诊 | 这是什么类型、该不该做 | triage |
| 澄清 | 需求内容里的歧义 | grill-with-docs |
| 定体量 | 澄清后按复杂度定 S / M / L | 内建启发式（本 skill 补充） |
| 拆解 | 拆成带依赖顺序的可执行单元 | to-tickets |
| 探路 | L 型：路径模糊时先拆决策地图 | wayfinder + OpenSpec |

## 流程

### 0. 输入识别

先判断需求源，这决定后续的「发布去向」：

- 输入是 GitHub issue（URL / `#编号` / `repo#编号`）→ 拉取 issue 全文 + 全部评论 + 标签 + 作者作为需求源；**发布去向 = 更新该 issue**
- 输入是自然语言 → 需求源 = 输入本身；**发布去向 = 创建新 issue**（GitHub 可用时）

### 1. 分诊（加载 triage）

调用 triage skill 完成：分类标签（bug / enhancement）+ 状态标签（needs-triage / needs-info / ready-for-agent / ready-for-human / wontfix），并遵守 triage 的全部规则（含发布到 issue tracker 的内容必须以 `> *This was generated by AI during triage.*` 开头）。

注意：**size 判定不在此步**——体量必须基于澄清后的完整信息来定，先澄清、后定大小（见 §3）。

### 2. 澄清（加载 grill-with-docs）

需求**内容**层面存在歧义时（术语含糊、行为未定义、多解场景），调用 grill-with-docs 逐项追问澄清，边聊边沉淀决策（ADR / 术语表）。

边界：此处澄清的是需求内容的歧义。若澄清后仍无法得出三要素中的某一项，**走 §5 缺口处理，不得继续追问**。

**无人工受访者时的处理**：grilling 是 HITL（需要真人参与对话）。若当前会话无人可问（后台 / 自动化执行），需求内容歧义**直接转 §5 缺口处理**——如实列入缺口清单（缺什么/由谁补/补在哪），不编造、不追问，由人工补齐后重新调度续接。

### 3. size 判定与路由（基于澄清后的完整信息）

澄清完成后信息已完整，**此时才判定体量**，打 `sized-s` / `sized-m` / `sized-l` 标签。

#### size 判定启发式

按优先级依次看三个维度：

1. **路径清晰度**：实现方案是否已明确？是否存在必须先决断的设计问题或未知领域？
   - 不清晰或存在未知 → 至少 M，倾向 L
2. **工作量**：能否在单个执行会话内完成（含测试与验证）？明显超出（多日、多人、多轮探索）→ L
3. **影响面**：涉及多少模块 / 服务 / 文件集合？单一 → S；2 个以上 → M 或 L

判定结果：

- **S**：路径清晰 + 影响面单一 + 单会话可完成 → 直接产出三要素分析（§4），作为单个任务
- **M**：路径清晰 + 需拆成多个依赖任务，但无需先期决策探索 → 产出三要素 + 调用 to-tickets 拆成带依赖顺序的任务清单（垂直切片、阻塞边、先做前置重构）
- **L**：路径不清晰（存在先决断问题）或明确超出单会话承载 → **必须拆分，禁止整块开工**，走下方 L 型路径

#### L 型路径：拆分 + 探路（wayfinder + OpenSpec）

L 型 = 超出单会话承载，**必须拆分才能推进**；拆分的正确对象是「决策」而非「任务」：

1. **wayfinder 拆决策地图**：把需求拆成 N 张**决策工单**——每张对应一个「必须先决断的问题」（服务边界怎么划、数据一致性怎么做、对外契约怎么定……）。一张工单 = 一个问题 = 一个执行会话的容量。工单间用**阻塞关系**接线；未被阻塞且未认领的工单组成 **frontier**（可立即开工的边界）
2. **逐张解决**：每张工单产出一个「决定」并关闭，直到全部解决、路径清晰
3. **全部决断后出 OpenSpec**：把已决断结论综合成 OpenSpec 提案（模板见 `references/openspec-template.md`）；此后才由 to-tickets 把执行拆成任务清单
4. 🔴 **硬规则：L 型禁止直接开工**——任何阶段都不实施、不写实现代码，只产出「地图 + 工单 + OpenSpec + 三要素」

**跟踪机制**：地图是索引（Destination / Decisions so far / Not yet specified / Out of scope），决策工单是地图的子项；解决一张 → 在地图「Decisions so far」追加一行索引 → 关闭工单 → 原先「Not yet specified」雾区里能精确表述的问题毕业为新工单。frontier 工单可被多个会话并行**认领**（认领 = 指派给自己）。无 GitHub 时降级为本地 markdown tracker（地图 = `decision-map.md`，工单 = `decision-tickets/<NN>-<slug>.md`）。

### 4. 产出三要素（任何产出必须包含）

无论 size 大小、无论是否缺失，产出的需求文档必须声明以下三项（可复制到 issue 正文 / 评论 / 落盘文件）：

#### 任务目标（Goal）
交付什么结果、用户得到什么。用**不含歧义的结果描述**（动词 + 可观察结果），而非过程描述。

#### 涉及范围（Scope）
改动影响哪些**文件 / 模块 / 服务**；以及**明确哪些不做**（非目标）。

#### 验收标准（Acceptance）
怎样算完成。**可操作、可验证、可复现**的判定条件（最好能对应到可执行的验证步骤，如「执行 X 后观察到 Y」）。

### 5. 缺口处理（三要素完整性检查）

三要素中任一要素**无法**从澄清后的信息得出时：

- ✅ 如实判定并标注「缺失」及缺失的具体要素名
- ✅ 给出补齐建议（具体到缺什么信息、由谁补、补在哪）
- ❌ **不得自行编造补全**
- ❌ **不得向用户追问**
- 产出文档保留缺口，状态标注 `awaiting-human-input` 并落盘；人工补齐后**重新调度本 skill 续接**（重跑时读取落盘文档，只补缺口，不复述已定内容）

### 6. 落盘与发布

**关键状态必须落盘**（三要素、size、标签、决策、任务清单），不得只存在会话中。落盘位置约定：

| 产物 | 位置 |
|---|---|
| 需求分析（三要素） | `.scratch/<feature-slug>/requirements-analysis.md` |
| 任务清单（M） | `.scratch/<feature-slug>/issues/<NN>-<slug>.md`（to-tickets 本地模式） |
| 决策地图（L） | wayfinder 本地 markdown tracker 模式（无 GitHub 时） |
| OpenSpec（L） | `specs/<slug>/proposal.md`（OpenSpec 标准布局） |

**issue 回写**：检测 GitHub 能力（gh CLI 已认证，或 GitHub 连接器可用）。

- **可用**：
  - **目标仓库**：优先取当前工作目录 git remote origin（若为 GitHub 仓库）；无关联仓库或无法确定时，需人工明确指定；无法确定 → 走降级
  - 输入来自 issue → 更新该 issue：发布分析评论（三要素 + 任务清单引用，必须带 AI 生成免责声明前缀），并更新标签（分类 / 状态 / size）
  - 输入来自原始输入 → 创建 issue：标题 = 任务目标摘要；正文 = 三要素 + 任务清单引用；应用标签
- **不可用 / 无法确定目标仓库** → **自动降级**：全部产物按上表落盘本地，并在分析文档顶部明确提示「需连接 GitHub 并指定目标仓库后执行 issue 创建 / 更新操作」，不阻塞分析主流程

## 硬规则清单

1. 🔴 **L 型禁止直接开工**：只产出地图 + OpenSpec + 三要素，不实施
2. 🔴 **关键状态必须落盘**：三要素、size、标签、决策、任务清单不得只存在会话中
3. 🔴 **三要素缺失不编造、不追问**：如实标注缺失 + 补齐建议，人工补齐后重新调度
4. 🔴 **发布到 issue tracker 的内容必须带 AI 生成免责声明**（triage 规则）
5. 🟡 有歧义才澄清：需求清晰时跳过 grill，不浪费轮次；**先澄清后定 size**，不提前拍板体量；L 型必先 wayfinder 拆决策工单，不跳过探路

## 依赖

- 子 skill（均已安装，本 skill 负责编排）：`triage`、`grill-with-docs`、`to-tickets`、`wayfinder`
- GitHub 能力：可选（不可用时自动降级本地落盘）
