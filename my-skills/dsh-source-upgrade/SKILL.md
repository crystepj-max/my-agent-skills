# DSH 源码升级、实例重启与配置对齐

## 先按用户目标选择路径

本技能覆盖三类独立任务：

- **升级源码**：用户要求更新 deepseek-harness checkout；按当前项目文档执行版本切换、构建和验收。只有目标明确包含让某个运行实例使用新代码时，才接着重启该实例。
- **重启实例**：定位用户指定或上下文明确的现有实例，核验其运行方式后重启并检查结果；不要强制升级源码或重跑升级验收。
- **对齐配置**：在用户指定的两个实例间同步所点名的设置与插件；不要顺带复制其他目录或助手配置。

已有授权按同一实例和影响范围复用。先核对当前活动任务与重启会造成的已知损失；只有发现此前未说明且会实质改变用户进度或风险的损失时，才就该变化询问。

## 每次执行前的现状核对

- 修改源码前先读当前 deepseek-harness/AGENTS.md（若存在）及其指向的项目约定。记录当前分支、HEAD、工作区状态和目标版本；使用 git status --porcelain=v1 -z -uall 等能保留路径边界的方式识别未提交内容。dirty checkout、未跟踪文件、未知分支和唯一产物都先保留。不得为升级切换或覆盖这些内容；遇到冲突时选符合项目规则的隔离工作目录，或报告准确阻塞。
- 从当前项目的 package.json、锁文件、版本管理文件、README/AGENTS 和可用 CLI 探测实际 Node、包管理器、入口命令与测试要求。旧记录里的 Node 24、pnpm、NODE_OPTIONS 和目录名均为历史线索，不是当前事实。只有确认某环境变量造成问题且项目约定允许时才移除它。
- 重启或探测前，从当前服务配置、进程参数和监听状态确认目标实例、实际端口、工作目录/DSH_HOME、启动管理器与对应日志位置。不要用历史端口或文件名猜实例；不明确时先完成只读定位。
- API key、cookie、launch token 等只在用户授权的目标实例操作中使用，绝不写入报告、日志、记忆或无关输出。不要自动复制第三方、其他助手或未点名实例的配置。

## 升级源码

1. **核对版本与仓库状态。** 确认当前 checkout、远端、目标 tag 和用户所说的“最新”含义，例如最新稳定版或指定版本。若需联网取 tag，按项目规则更新 tag；不要顺手 prune 远端或本地引用。比较目标 tag 的提交与 package version，并检查发布说明。
2. **保留现有工作。** 只有工作区状态和项目约定都允许时才切换。保留原分支、dirty/ignored 内容及其他工作；不能在当前 checkout 安全切换时，使用符合项目规则的隔离副本，或说明需要处理的具体冲突。
3. **按当前项目契约安装并构建。** 从项目文档和锁文件选择包管理器、运行时及命令。只针对当前证据表明的 Node ABI、注入环境变量或依赖问题做调整。不要因旧例中的错误就删整个依赖树、重装全部包或套用固定版本。
4. **保留完整升级的三项验收。** 完整源码升级默认核验当前存在的 CLI/源码入口版本一致、真实 LLM e2e、隔离 web profile 启动与访问；按当前项目文档查找实际入口与命令，不能因旧路径变化而省去验收目标。只有用户明确把任务限定为 checkout 更新时，才不重启常驻目标服务。
5. **真实 LLM e2e。** 完整源码升级默认包含真实模型调用，使用当前项目支持的凭据注入方式；不要把 key 输出到命令、进程参数、报告或日志。凭据来源或服务端能力缺失时，把该项标为未验证并报告具体缺口，整体结论标为部分完成，不把构建通过说成完整升级通过。restart-only/config-only 请求不运行升级验收。
6. **隔离 web profile 启动与访问。** 完整源码升级默认在隔离 profile 中启动并核验访问；使用当前项目的启动命令和健康判据。记录本轮临时探针的 PID、启动参数与产物，结束后只停止该临时探针。目标常驻服务须按用户目标保留运行。若完整升级还需让常驻实例使用新代码，操作精确目标并检查其活动任务；重启后结合当前版本支持的健康检查、监听状态及限定目标日志判断。

## 重启已运行实例

从当前服务配置、启动管理器、进程命令和监听状态确认目标实例。先查看该实例的活动会话、临时插件注入和未保存工作流状态，再使用当前项目记录的重启方式；已有授权按目标与影响范围复用。启动方式、端口和健康检查都以当前仓库与宿主能力为准。

若用户是在恢复访问，可把目标实例当前有效的登录链接提供给用户，或在其授权浏览器中打开。链接里的 launch token 属凭据：仅在当前授权目标内使用，不写入报告、日志、记忆或无关输出。认证有效期、端口绑定规则及重启后失效行为须按当前源码/配置核实，不引用历史天数作为保证。

## 实例间配置对齐

先确认用户指定的源实例、目标实例，以及“对齐”具体包括哪些设置。读取双方当前项目说明与配置结构，列出将改变的目标字段；保留其余目标侧配置。当前配置文件名、插件目录和命令均须从所选实例实际目录及 CLI 查证。

- 仅同步用户点名的模型选择、供应商参数或插件定义。不要把整份配置、运行目录或其他助手/第三方工具配置自动复制到 DSH。
- 插件按当前 DSH 文档支持的安装命令在目标实例安装；只有确认安装方式不可用、源与目标兼容且覆盖范围明确时，才考虑迁移已有实体。固定包名、下载超时阈值、目录体量与 rsync --inplace 都是历史案例，不作为默认路径。
- 比较必要的非敏感字段，先脱敏再输出。避免把配置 dump、日志或整个配置写到公开临时路径；不要把 API key、cookie、token 或凭据文件内容加入 diff。
- 不自动复制密钥。若用户明确授权在两个指定的自有 DSH 实例间同步凭据，只能使用当前项目支持的安全路径且不得显示或留存明文；若工具权限或项目约定不允许，说明准确缺口。模型连通性按用户目标使用安全的真实调用验证；不能把文件存在或进程打开文件当成调用成功。
- 备份仅限本次明确修改的目标文件，存到符合项目政策且不进入版本库的位置。不要借备份删改无关内容。

## 历史故障模式：先证据、后处置

以下是过往排障中出现过的线索，不是当前环境事实，也不授权批量清理或修改插件。每次先从目标仓库源码、当前错误、锁文件内容、进程身份和项目文档确认。

### Git 引用与 profile 写锁

针对报错中点名的确切引用或 profile 锁，先核对锁路径、内容格式及当前可能的写入者；如果持有者、用途或所属 checkout 不明确，保留锁并说明阻塞。不能用 lsof 无输出、时间久或进程未找到单独证明锁可删。不要扫描并删除所有 .git/**/*.lock，不要用 Python os.remove/shutil.rmtree 绕过 safe-delete 或仓库保护。优先使用当前项目提供的恢复命令；没有可靠恢复路径时停在具体锁并报告。

### Node ABI 与环境变量

若错误包含 NODE_MODULE_VERSION，从运行中进程和当前项目声明核对实际 Node 与原生模块 ABI，再选择项目支持的运行时。Node 22/24、ABI 127/137 只是历史示例。仅当当前命令证据表明某个 NODE_OPTIONS 注入造成问题，且项目约定允许时才针对该命令移除。

### 插件启动失败

如果目标实例因插件加载失败，先读该版本 DSH 与该插件的真实错误、兼容说明和受影响实例。禁用、升级、回滚插件或源码都属于会改变用户环境的处置，执行前确认它属于用户当前目标；不得仅凭发布日期、旧错误样例或旧 patch 位置自动改配置。

### 构建与临时探测

识别当前项目对构建与后台执行的实际要求。启动临时进程时记录本轮创建的 PID、启动参数和临时产物；清理时核对 PID 仍对应本轮命令，并只处理本轮新建且确认可丢弃的文件。不要使用 pkill -f 宽匹配进程，也不要因某宿主历史行为推断后台任务必定被回收或必定常驻。

## 完成说明

按用户目标分别报告：实际改动的仓库/tag/配置或实例、当前构建与必要验收结果、是否已应用到服务、未验证的原因，以及保留的冲突或资产。不要只按固定分钟数停止，也不要因时间预算把已明确目标静默降级；出现真实阻塞时给出事实和可继续路径。测试范围遵照当前项目要求与用户目标，不把历史耗时或平台例外当作当前规则。没有用户授权时不提交、推送或发布。
