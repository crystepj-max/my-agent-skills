# Skill Workbench

帮助用户从零创建、维护或验证一个 agent skill。先判断本次实际目标，再选择最小足够的流程。用户已经给出目标和约束时，从对话、文件和已有工具中提取信息，直接推进；不强制访谈、重新确认已知事项或运行整套评测。

## 工作约定

- 工作目录、skill 名称、适用 agent 格式和交付方式由用户请求及仓库约定决定；不要擅自改名或覆盖现有 skill。
- 新 skill 至少应有正确 YAML frontmatter（`name`、`description`）和能完成目标的正文步骤。正文应写触发后的执行路径、关键分支、输入输出、必要安全边界和完成条件。
- 复用当前仓库的 `AGENTS.md`、已有相关 skill、模板和工具。不要把引用文件、脚本或素材从包里删掉却不改引用。
- 评测方式取决于改动：小型文字修订可做 frontmatter/YAML/链接检查和定点场景检查；影响关键行为、路由或多分支流程时，准备少量代表性正反场景并验证。全面 benchmark、基线运行、人工评分或盲测都属于可选加强项，只有用户需要且环境、时间与费用合适时执行。
- 评测只能证明实际覆盖的场景。写清没有运行的项目；不要把静态文字检查描述成行为验证。

## 1. 确定要交付的变化

读取用户请求、目标 skill、引用文件和必要的仓库约定。先整理：目标用户任务、何时应触发、已有有效能力、当前具体问题、验收方式。已有对话或文件足以回答时不要重复提问；只问会实质改变范围或风险的缺口，并先完成不依赖该答案的工作。

如果是在现有 skill 上工作，记录其文件清单和重要引用，保留原始能力；如果用户要求全新 skill，按项目命名规则确定目录名。`name` 字段应与目录标识一致。description 说明做什么以及何时使用，避免把泛化宣传词当触发条件。

## 2. 编写可执行的 skill

先写主流程，再加入必要参考资料或脚本。按用户体验组织步骤：

1. 识别输入并查找现成信息；
2. 选择主路径和重要分支；
3. 执行可逆的本地工作；
4. 对删除、外发、发布、付费、提交等有影响的动作遵循明确授权；
5. 检查结果并交付证据、路径和限制。

每条规则都应改变行为或减少歧义。能写成条件分支时，不要用一长串绝对命令要求每个请求走同一流程。把大型领域细节放入有明确加载时机的 `references/`；可重复且确定的计算放入 `scripts/`；输出格式模板放入 `assets/`。验证每个指针真实存在、目标内容仍与主 skill 一致。

## 3. 按改动风险选择验证

先用成本最低且能发现目标故障的检查：

- **元数据/文案改动**：解析 frontmatter/YAML，核对名字、说明和本轮调整的具体场景；检查技能链接、脚本和素材路径。
- **新增或变更执行步骤**：用一条代表性请求推演输入、分支、输出和完成条件。对可观察行为，运行目标脚本或在隔离 fixture 中验证。
- **多种触发场景或争议性路由**：准备少量应触发/不应触发的近邻请求。必要时分别按 skill 前后版本执行并比较用户相关输出。
- **高影响行为、用户要求定量比较**：使用 `evals/evals.json` 和 `scripts/run_eval.py`、`scripts/aggregate_benchmark.py`、`eval-viewer/generate_review.py` 等配套工具。先说明会运行哪些场景、需要什么模型/服务和预计资源，再执行。留存提示词、输入、输出、评分依据、版本和失败情况。

本包的部分自动触发工具针对 Claude Code 的 `claude -p` 和 `.claude/commands/` 设计；它们不代表当前 Codex/其他 agent 的触发行为。只有目标运行环境与工具匹配时才用这些结果判断触发率；否则采用目标环境中真实可用的调用/人工场景。不得为了让工具跑通而安装 CLI、登录账号或产生费用，除非用户要求并授权。

小改动通常不需要长周期 benchmark。全面测试集、with/without 对照、评审网页、定量 grader、描述优化、盲比较和多轮迭代都是可选项。若使用，范围应与风险相称，设定明确停止条件；用户未要求时不强制等待人工评审，也不无限循环优化。

### 可复用评测数据

如果需要记录评测，放在目标 skill 的 `evals/evals.json` 或项目已有位置。每个案例写真实用户会提出的请求、必要输入文件和可观察的预期结果；正向场景之外要有关键近邻负例。只为客观行为写可机器判定的 assertion，写作、设计和价值判断仍需人工评价。

比较现有版本时，把旧版作为只读基线快照保存在 workspace，不覆写唯一原件。新 skill 可与不加载 skill 的基线比较。避免一次改变多个行为后用一个总分掩盖回归；发现失败后先定位相应场景，再决定是否修改。

### Frontmatter 与宿主兼容字段

基础结构检查应保留未知顶层键拒绝，避免把拼写错误误判为有效配置。除常见的 `name`、`description`、`license`、`allowed-tools`、`metadata`、`compatibility` 外，也支持在其他 agent 宿主或发行包中已有的调用字段：`disable-model-invocation` / `user-invocable`（布尔）、`argument-hint`（字符串）。这些字段控制显式调用或参数提示，不能为了通过某个宿主的窄 validator 而删除。

对已发现的供应商扩展采用明确白名单并检查类型：`version`、`namespace` 为字符串；`disable`、`agent_created` 为布尔；`platforms` 为字符串列表；`commandHint` 为映射，其中已知的 `argumentHint` 为字符串。验证器仅检查结构，不推断这些扩展在当前宿主中的运行语义。来源、分类、风险、署名和分发标签等治理信息优先放在 `metadata`；许可证与署名内容仍须保留。

## 4. 检查配套工具

脚本应说明依赖、输入格式、输出位置和限制。运行脚本前读帮助或入口代码；使用临时目录和小型 fixture，避免把基准或测试结果写进源包。可用的主要工具包括：

- `scripts/quick_validate.py <skill-dir>`：检查技能结构与 frontmatter；需要 PyYAML。
- `scripts/package_skill.py <skill-dir>`：打包可分发文件；先检查生成路径和包内文件。
- `scripts/run_eval.py` / `scripts/run_loop.py`：在其支持的 Claude CLI 环境运行触发评测；会调用模型，评测范围、次数、费用应先明确。
- `scripts/aggregate_benchmark.py`、`scripts/generate_report.py` 与 `eval-viewer/generate_review.py`：汇总现有运行结果或查看定性反馈，不会替代人工判断。

若工具不适配当前环境，使用等价的小型验证并如实标记；不要为了形式运行整套脚本。

## 5. 交付与维护

交付包含 skill 路径、主要行为变化、保留或新增的能力、实际验证与未验证部分。保留 LICENSE、署名、依赖、引用文件和原作者说明；来源或许可证不明确时不要臆测。用户要求打包时，再生成 `.skill` 包并说明输出位置。

优化完成后，可以建议下一步是否做更广评测，但无需等待用户确认才能交付已授权的修订。不要自动改名、提交、推送、发布、安装到其他发现目录或修改外部仓库。

## 深入资料

仅在相应任务需要时读取：

- [references/schemas.md](references/schemas.md)：评测数据、grading、benchmark 的文件结构；
- [agents/grader.md](agents/grader.md)：针对已有 assertions 的评分原则；
- [agents/comparator.md](agents/comparator.md)：应用户要求做盲评比较；
- [agents/analyzer.md](agents/analyzer.md)：解释已有 benchmark 的差异。

这些文件和脚本保留为可选能力。简单修订可以只运行元数据解析、链接检查和一两个有区分度的场景。
