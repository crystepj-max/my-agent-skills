# 多 worktree 工作区体检与收敛（只读审计 + 报告）

## 何时用

一个 Git 仓库同时开着多个独立分支或工作树并行开发，出现过程产物散落、归属不明、目录嵌套、磁盘占用异常、收口后残留、worktree 登记与磁盘状态不一致等情况时，用本技能做只读盘点和收敛规划。

## 何时不用

| 场景 | 处理方式 |
|---|---|
| 目录搬迁/改名后的路径引用修复 | 使用当前会话实际可用且适用的工具/技能；若没有，说明修复能力缺口，不阻断本次独立审计 |
| 整机磁盘占用分析 | 使用当前可用的磁盘分析能力；若不可用，说明缺口 |
| 单次 merge/rebase 冲突 | 按当前仓库冲突处理文档和本次授权操作 |
| 只要删除一个明确工作树 | 按用户原始请求和当前仓库文档处理；本技能不把它扩大成全工作区清理 |

## 审计边界

1. 对工作树、分支、任务与产物的盘点和分类保持只读；可按本次请求写审计报告。报告路径使用用户指定位置或当前任务交付目录，不默认写长期记忆。
2. 单纯要求审计/规划时，只交付报告和建议，不执行删除、移动、改名、git worktree remove、prune 或 branch -d。
3. 如果原始任务明确授权了具体清理目标，主助手在审计后依原授权接续；只处理核实属于该目标的资产。切换阶段不使授权失效。发现新目标、新资产类别或实质性数据损失风险时，只就变化部分再确认。
4. 未知归属、唯一副本、dirty/ignored 内容和未识别分支默认保留并标为待判定。

## 为什么这个体检值得做

多 worktree 工作区混乱常由产物锚点不清和生命周期没有定义引起。体检要回答产物归属在哪里、当前有哪些分支与工作树，以及项目约定的档案是否齐备。命名统一只是附带结果；报告应以当前证据说明问题，不把历史经验写成当前规则。

## 诊断流程

### 步骤 1：列出工作树与登记

~~~bash
cd <仓库>
git worktree list --porcelain -z
git worktree prune --dry-run --verbose
git rev-parse --git-common-dir
~~~

dry-run 输出只说明 Git 识别到候选登记，不代表候选目录或其中内容可以删除。主检出通常不在公共 Git 目录的 worktrees 子目录中。若交叉核对数量，先用 git-common-dir 定位实际公共 Git 目录，再区分主工作树与 linked worktree；数量差异只作为线索，不能单独判定孤儿或清理对象。

### 步骤 2：建立逐工作树映射

逐项记录路径、分支或 detached HEAD、HEAD、未提交状态、任务归属与主分支关系。交互查看可读取 git worktree list --porcelain 和各工作树状态；自动化解析时使用 git worktree list --porcelain -z 及 NUL 安全解析，并用 git status --porcelain=v1 -z -uall 保留空格、换行路径及未跟踪文件边界。

rename/copy 状态可能包含两个路径，解析时按 porcelain 规格读取 NUL 分隔字段；不要用空格分词、按输出行数统计脏文件，或根据工作树目录名推断分支。主分支名、远端来源和合并方式以当前仓库为准；遇到 squash/cherry-pick 时检查仓库记录，不依据祖先关系单独判定可清理。

### 步骤 3：核对任务与归属

先确认当前仓库是否有任务登记册、分支映射或归档约定；仅在存在时按其真实格式对账。不要把某一仓库的 registry、状态词或“三件套”结构当作所有项目的必需合同。缺少登记时标注“未找到归属证据”，不虚构任务状态。

重点标出登记指向不存在的工作树、存在但找不到任务归属的工作树，以及终态任务仍有工作树或过程产物的情况。终态标签只提供线索，不能独自授权清理。

### 步骤 4：检查内容与体量线索

按仓库文档检查相关工作树、运行时工作区和项目产物目录。只测量已确认属于本次审计范围的路径；不要因历史示例中的目录名而扫描用户整个临时目录或其他助手配置。

目录体量、依赖目录、时间戳和相邻工作树的大小差异仅是调查线索，会随项目、平台与生成物变化。不能用固定体量或时间阈值推断归属、可重建性或删除安全。

### 步骤 5：核对嵌套与 Git 指针

检查工作树路径之间是否存在嵌套，并双向读取 linked worktree 的 .git 指针与 Git 管理目录中的 gitdir 路径。指针不一致时，避免在归属未明的目录执行会写索引/HEAD 的命令，并核查目录下 ignored 与未跟踪文件。

路径嵌套或指针不一致只说明需要调查；不得据此整体删除。未知持有者、唯一产物和其他工作树的引用都先保留。

### 步骤 6：核对项目定义的任务归档

工作树干净、任务已合并或工作树已消失，都不能单独证明项目档案完整。若当前仓库明确规定任务卡、规格、运行证据或其他归档内容，按该项目的终态记录逐项核实，并区分“无归档证据”和“确认缺档”。没有对应项目契约时，不强制生成或补写材料。

检索缺失材料时以项目约定的相关目录为范围，可包含被忽略的临时目录；不要扩展到无关用户数据。发现唯一副本时记录位置并标记保留。重复内容要列出副本、完整性、引用关系和所有者，再给出建议；审计阶段不迁移或删除文件。

## 分类标准

| 分类 | 判定条件 |
|---|---|
| **清理候选** | 终态证据齐全、版本控制状态已检查、ignored/未跟踪产物已核对、没有唯一内容或活动引用，且本次请求授权了该具体清理 |
| **保留（进行中）** | 当前任务、活动引用或未完成工作证据表明仍在使用；项目状态词以实际登记为准 |
| **保留（有独有提交）** | 分支有尚未能映射到远端/主线/PR 的唯一提交，或归属未明 |
| **待判定** | 无归属、唯一资产、ignored 内容、系统临时目录、运行时半成品或状态无法确认 |
| **异常（优先调查）** | 孤儿登记、指针异常、悬空引用或漏网产物；异常本身不构成删除授权 |

## 检查时的注意点

### 合并方式

若仓库使用 squash 或 cherry-pick，原始分支提交可能不是当前主分支的祖先。核对合并提交、PR/任务记录和提交树内容，不仅看 merge-base 的结果。

### 目录名与分支名

工作树目录名与所检出的分支名可能不一致。分支和 HEAD 必须从当前 Git 状态读取，不能根据目录名推断。

### 工作树、分支与过程产物

工作树目录、分支历史和被忽略的过程产物是不同资产。清理其中一项不等于另外两项可删；在报告中逐项列明关系、归属与唯一内容。

## 清理计划的边界

报告可以按资产列出建议动作、依据、数据损失风险和未解决问题，但仅审计请求下不执行任何清理。若原始任务已明确授权具体对象，主助手按现有授权接续，先核实对象仍匹配、归属和删除范围；报告中的“候选”不自动扩大授权。遇到权限、钩子或退出码不一致时，先只读复核实际状态，不重试宽范围或强制删除。运行时拥有的工作区优先用该运行时正式回收方式，并遵循当前仓库文档。

未知资产、未知持有者、dirty/ignored 内容和唯一副本保持原状。不要按固定批次数、时间阈值、进程查询空结果或特定机器的 safe-delete 行为裁定安全。

### 核查内部过程产物

git status 为空不等于没有有价值内容。agent-runs、scratch 或其他被 gitignore/.git/info/exclude 排除的目录可能含任务证据、运行数据或唯一文件。按当前仓库 ignore 规则和工作流产物目录逐项核查；机器解析状态必须使用 NUL 分隔，不能只依赖行数或状态为空。

审计时记录内部产物与仓库归档位置是否一致；如果缺少唯一副本或归属无法确认，将其列为待判定并保留。报告不自动补归档。只有原始任务已明确授权该项归档/清理时，主助手按该范围接续。

## 治理建议（体检之外的产出）

体检报告可以提出结构性治理建议，但要区分当前事实与未来设计方向：

1. **单一锚点**：建议明确过程产物应该进入主检出、任务归档还是外部存储；从当前仓库文档核实实际路径，不从 git-common-dir 直接推断主检出。
2. **统一命名**：若项目需要，可为任务、分支、工作树与产物建立可追踪关联；保留现存合法命名和历史资产。
3. **生命周期**：建议明确什么内容在何事件后处理；保留期的执行应基于项目认可的事件与内容所有者，不用固定时间自动删除唯一数据。
