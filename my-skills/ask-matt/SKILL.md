# Ask Matt

把用户要完成的事带到一个明确、可复核的结果。先理解请求和当前工作区，再建议或直接使用最短的适合流程；不要要求用户先安装一整套流程，也不要把工具配置、工单或分支仪式当作目标本身。

## 1. 识别当前阶段

从用户原话和已有上下文判断其要的是：

- **探索/决策**：先查现有事实；需要用户选择时，提出少量关键问题。`grill-me` 适合不需要留下项目文档的讨论；`grill-with-docs` 适合需要把术语、决定或 ADR 留在当前项目的讨论。
- **研究**：针对易变或不确定事实查官方文档、源码或其他一手材料；用 `research` skill 或直接完成研究，逐条记录来源、时间与限制。仅在并行阅读能节省时间时才委派。
- **原型**：当一个可运行的界面或行为能更快回答问题时，当前会话中有 `prototype` 技能才调用；缺少该技能时直接原生完成最小原型，不以技能缺失为阻断，也不恢复旧版。交付原型、问题和证据；生产实现是单独选择。
- **需求定义**：从现有 spec、issue、README、设计文档和对话提取目标、范围、验收标准与未决问题。可用当前可见的 `requirements-analysis`；不可用时直接按这些字段写出等价计划。项目级 workflow 若确实适用，可使用 `wf-explore` 或 `wf-construction-full-feature`。
- **实施**：用户已明确要改代码时直接实施；依据仓库 `AGENTS.md` 和现有检查流程。多任务只有在依赖清楚且真实可并行时才用 `implement-spec`；没有合适的并行能力就按依赖顺序逐项做。
- **故障处理**：先复现用户看到的问题，定位最小原因并验证修复。项目有 `wf-diagnose` 时可使用；否则按同样过程完成，不要求安装额外技能。
- **审查/发布准备**：用 `code-review` 检查明确范围；当前会话中有 `pr` 技能才调用来起草 PR 描述，缺少时直接按本技能完成，不以技能缺失为阻断，也不恢复旧版。是否提交、推送、合并、发布或关闭 issue 由用户的明确授权决定。
- **复盘**：用户要求时，当前会话中有 `retro` 技能才调用；缺少时直接原生总结环境改进，不以技能缺失为阻断，也不恢复旧版；不要借复盘擅自改项目配置。

## 2. 保留当前信息

在一个任务的连续步骤中，保留用户目标、已确认选择和验证证据。上下文很长时，按平台现有的压缩能力整理成短摘要；需要交给新会话、工作目录或同事时用 `handoff` 生成可独立阅读的文件。上下文管理和阶段切换采用当前平台真实可用的能力；不要把已退役的命令当作前置条件。

## 3. 任务拆分和协作

只有工作确实独立、能节省时间或改善验证质量时才并行；明确每项输入、输出与完成条件。共享文件或同一环境由一个写入者协调，其他工作者准备独立结果供集成。跨会话的大目标可用 `wayfinder` 持续推进真实未决问题；它不限制每会话只做一项。

每个交付包含用户关心的结果、主要证据、已做的检查和仍未验证的部分。需求缺失时区分“无法核对需求”与“代码实现不符合需求”，而不是停下全部工作。

## 4. 仓库或工具配置

只有当前任务真的被缺少凭据、命令、tracker 或协作约定阻塞时，才读取相关配置或引导配置。先查看仓库内的 `AGENTS.md`、README、现有脚本、CI 和已连接工具；能用本地文件完成就不要求先配置外部 issue tracker。配置需要用户提供的秘密或外部写入时，先把具体内容准备好，再仅询问缺失的值或授权。

## 常用路径

- 新点子，且可以在一轮内定清：`grill-with-docs` → 需求/验收摘要 → 用户要求时再实施。
- 范围大、问题尚未排清：`wayfinder` 持续梳理依赖和决策；决策明确后交给 `requirements-analysis` 或 `implement-spec`。
- 已定义的单项工程任务：直接阅读项目说明并实施；结束后用 `code-review` 做独立检查。
- 难以描述的交互：当前会话中有 `prototype` 时使用它；否则直接做最小可运行版本并交付行为证据。
- 外部问题/请求队列：`triage` 先做证据核实；issue 状态、评论、关闭等写入按明确授权执行。

以上是选择工具的提示，不是强制流水线。用户已说清下一步时直接做该步，不重复要求其确认已经给过的信息。
