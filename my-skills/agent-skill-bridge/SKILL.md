# 技能统一管理

第一方执行入口与使用范围由本仓库 `inventory/skill-policy.json` 决定；不要把公共池全集当成所有助手的必装列表。

1. 读取登记表及当前入口，核对维护源与完整配套材料。第一方源是执行入口；已被第一方完整覆盖的第三方包保留在发现目录外作完整参考，后续只比较上游变化并把审阅过的改进合入第一方，不能用第三方原件覆盖第一方。用户决定从现存原件建立第一方维护源时，记录“自此由第一方维护”，保留完整原件，并把未证实的原作者/来源继续标为 unknown。M1 `requirements-analysis` 由 workflow-manager 维护并直接分发到用户级目录；M3 `execution-plan` 由 dev-flow 维护为项目级 Skill；M2 单任务交付由 workflow-manager 蓝图生成。此仓不镜像、不登记、不分发 M1/M3。
2. 运行 `python3 scripts/bridge.py --mode dry` 生成计划；按对象、范围、版本和影响复用已有授权，不重复批准。只对无法查明且会实质改变目标、范围、接收对象、验收、费用或风险的缺口提问；局部冲突只暂停受影响项，独立项继续。
3. 运行 `python3 scripts/bridge.py --mode apply` 按范围落地；替换入口前保存备份。只有 active 的第一方全局源作为完整执行入口；transition 仅用于尚无第一方覆盖且登记说明了缺口的能力。reference 和 retired 均不进入发现目录；项目级能力只进入指定项目。
4. 运行 `python3 scripts/bridge.py --mode verify` 核对该出现的出现、不该出现的不出现。第一方使用同一维护源，不能只比对名称或 SKILL.md 而忽略配套脚本。
5. 向用户报告实际变化、冲突、缺失及需刷新会话的范围。已安装不等于当前会话已重新加载。

## 范围与发布

- 不修改插件缓存、宿主内置技能或未知独有入口来“凑零缺失”。插件重叠只报告；用户明确授权的具体插件修正另行处理其正式来源。
- 不把备份放在技能发现目录。去重按技能声明名与来源判断，目录加日期不能视为停用。
- 只有登记明确说明“第一方尚未覆盖”的第三方能力可保留为 transition；不得在 active 第一方已覆盖时把 transition 当执行回退。reference 只供对照，不执行整套安装/退役流程；retired 不恢复到发现目录，项目级条目不提升为全局。
- 新安装来源按用户要求核验安全与必要资料；无须给未新增来源的本地规则文字调整套用安装流程。
- 本地应用、检查、恢复均不自动提交或推送。用户明确要求发布时只提交已审阅的指定文件；不得把整个工作区无关改动一起提交，不强推或强制推到 main。
- 本技能脚本是入口，调用本仓库 `scripts/manage-skills.py`。仓库不存在时说明缺少维护源，不从安装副本反向覆盖仓库。

## 中文化：description 必须译为中文

**第三方 skill 的 frontmatter `description` 一律译为中文**，正文保持原语言不译。这样 `/` 命令与各助手的选择列表可读，也便于人工核对。

装完或从上游更新后跑一次守护：

```bash
bash ~/.agents/skills/agent-skill-bridge/scripts/cn_guard.sh          # 登记表内 active/transition
bash ~/.agents/skills/agent-skill-bridge/scripts/cn_guard.sh --all    # 并查未登记条目
```

退出码：`0` 通过 / `1` 有纯英文或缺失需翻译 / `2` 环境异常（维护源缺失、目标不可读、校验范围为空）。

两条硬规则：

- **只读，不自动改写。** 翻译需要 LLM 判断，脚本只如实报告，由 agent 用 Edit 逐项写入。旧 `cn --fix` 已移除——无人审阅的自动写入会覆盖已核对的中文描述。
- **退出码是唯一可信信号。** 早期实现用 `grep` 匹配输出来判断，工具报错时 grep 无匹配 → 误判「通过」并 exit 0，是**假绿灯**，会骗过 CI。判断成败只准看退出码，不准解析输出文本。

判定英文用两级顺序：中文占比 ≥ 15% 即放行（技术类中文描述常内嵌成串英文，如报错原文、API 名、CLI 参数），否则看是否存在连续 4 个以上英文单词。阈值与检测逻辑在 `manage-skills.py` 的 `needs_translation()`，回归见 `tests/test_cn_guard.py`。

## 语义重复：不同名同物（登记表查不出来，必须人工判）

`manage-skills.py plan` 只按声明名与来源判断重复，**不同名但功能重叠它查不出来**。这类重叠里最高频的是新旧两代并存，判法如下。

**旧版自声明是替代关系的依据之一，不是必要门槛；描述相似本身不构成处理依据。** 可检查旧版是否写明替代/退役条件：

- `shim-map.md` / `runbook.md` 的「退役纪律」「收敛路径」「最终形态」小节
- `README.md` / `meta.json`（生成物常标 `蓝图真源`、`生成物不可手改，改蓝图重生成`）
- `skill-policy.json` 里的 `invocation: explicit-legacy-only` 或 `state: transition` 只是复核线索；应核对实际替代条件、承接范围和登记

旧版自声明明确且承接方已登记、覆盖范围已核验，可以作为替代证据；或者，用户当前明确选定替代方、承接范围已核验并正式登记，也足以确认替代关系，不必等待旧版自声明。若原第三方包继续供对照，保留完整原件、来源、恢复边界和未审阅本机差异，登记为 `reference` 并移出发现目录；这不等于退役。只有确实决定并完成退役时才标 `retired`。仅功能相似且没有上述授权/承接证据时保留原状态，不删除。

**别用内容哈希跨池找重复。** 桥接是软链（`~/.workbuddy/skills/x` → `~/.agents/skills/x`），从两个池读同一个 skill 得到的是同一文件，指纹必然相同，整池会全部误报为重复。要比就比不同名条目，且先解析软链真实路径。

**只有确认该条目确实退役时，才执行以下三件事**，少一件等于没退；保留作对照的 `reference` 不标 `retired`：

1. `skill-policy.json` 里置 `state: retired`，`source` 改指 `~/.local/share/agent-skills/retired/<name>`（已有先例，注意该目录在 git 之外，PR 里只会看到登记表的条目变化）。
2. 目录移出发现目录（`my-skills/` 与 `~/.agents/skills/`），不能只改表不挪目录，也不能只删目录不改表。
3. 派生文档 `skill-lifecycle.md`、`skill-desc-translation.md` 同步；它们由登记表派生，改表后必须跟着改，改它们不改表没有意义。

**登记新版时顺手查 UNMANAGED**：`plan` 输出里的 UNMANAGED 项没有进入登记表，退役旧版前先确认承接方已在表中，否则退役后正式入口缺失。指纹用 `manage-skills.py` 自己的 `fingerprint()` 算，不要自己实现。
