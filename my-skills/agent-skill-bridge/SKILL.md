# 技能统一管理

第一方执行入口与使用范围由本仓库 `inventory/skill-policy.json` 决定；不要把公共池全集当成所有助手的必装列表。

1. 读取登记表及当前入口，核对来源与完整配套材料。第一方维护源在 `my-skills/`；需求、建设、调度三项须先在 workflow-manager 的 `dsh/skills/` 修改，再同步到这里。
2. 运行 `python3 scripts/bridge.py --mode dry` 生成计划；用户已有明确调整授权时直接继续，不逐项重复批准。确有未决用途或不同本机修改时保留冲突，仅暂停相关项。
3. 运行 `python3 scripts/bridge.py --mode apply` 按范围落地；替换入口前保存备份。正式与过渡全局项才进入公共池；参考和退役项保存在发现目录以外；专业能力进入指定项目。
4. 运行 `python3 scripts/bridge.py --mode verify` 核对该出现的出现、不该出现的不出现。第一方使用同一维护源，不能只比对名称或 SKILL.md 而忽略配套脚本。
5. 向用户报告实际变化、冲突、缺失及需刷新会话的范围。已安装不等于当前会话已重新加载。

## 范围与发布

- 不修改插件缓存、宿主内置技能或未知独有入口来“凑零缺失”。插件重叠只报告；用户明确授权的具体插件修正另行处理其正式来源。
- 不把备份放在技能发现目录。去重按技能声明名与来源判断，目录加日期不能视为停用。
- 第三方尚未被替代的能力可登记为 transition；已是 reference 的不能执行其整套审批和停止流程。
- 新安装来源按用户要求核验安全与必要资料；无须给未新增来源的本地规则文字调整套用安装流程。
- 本地应用、检查、恢复均不自动提交或推送。用户明确要求发布时只提交已审阅的指定文件；不得把整个工作区无关改动一起提交，不强推或强制推到 main。
- 本技能脚本是入口，调用本仓库 `scripts/manage-skills.py`。仓库不存在时说明缺少维护源，不从安装副本反向覆盖仓库。

## 语义重复：不同名同物（登记表查不出来，必须人工判）

`manage-skills.py plan` 只按声明名与来源判断重复，**不同名但功能重叠它查不出来**。这类重叠里最高频的是新旧两代并存，判法如下。

**判据不是描述像，而是旧版自己有没有写退役条件。** 先在旧版目录内找自声明：

- `shim-map.md` / `runbook.md` 的「退役纪律」「收敛路径」「最终形态」小节
- `README.md` / `meta.json`（生成物常标 `蓝图真源`、`生成物不可手改，改蓝图重生成`）
- `skill-policy.json` 里的 `invocation: explicit-legacy-only`、`state: transition` 也是过期信号

命中就走「先登记新版 → 再把旧版置 retired → 目录移出发现目录」；**未写退役条件的重叠一律保留**，不凭相似度删。

**别用内容哈希跨池找重复。** 桥接是软链（`~/.workbuddy/skills/x` → `~/.agents/skills/x`），从两个池读同一个 skill 得到的是同一文件，指纹必然相同，整池会全部误报为重复。要比就比不同名条目，且先解析软链真实路径。

**退役必须做满三件事**，少一件等于没退：

1. `skill-policy.json` 里置 `state: retired`，`source` 改指 `~/.local/share/agent-skills/retired/<name>`（已有先例，注意该目录在 git 之外，PR 里只会看到登记表的条目变化）。
2. 目录移出发现目录（`my-skills/` 与 `~/.agents/skills/`），不能只改表不挪目录，也不能只删目录不改表。
3. 派生文档 `skill-lifecycle.md`、`skill-desc-translation.md` 同步；它们由登记表派生，改表后必须跟着改，改它们不改表没有意义。

**登记新版时顺手查 UNMANAGED**：`plan` 输出里的 UNMANAGED 项没有进入登记表，退役旧版前先确认承接方已在表中，否则退役后正式入口缺失。指纹用 `manage-skills.py` 自己的 `fingerprint()` 算，不要自己实现。
