# Code Review

检查用户指定范围内的改动，给出可定位、可复核的发现。默认只审查，不改代码、不提交、不推送、不合并，也不替用户关闭 issue。只有用户明确要求同时修复时，才在报告后转入修改，并保留审查与修复的边界。

## 1. 确定审查对象

先查看 `git status --short --untracked-files=all`、当前分支和 HEAD。按用户说的目标选择范围：

- **当前工作区**：同时检查 unstaged、staged 和未跟踪文件。分别读取 `git diff` 与 `git diff --cached`；用 `git ls-files --others --exclude-standard -z` 得到未跟踪路径，按 NUL 分隔读取并逐一打开（不要用按空格拆路径的命令）。不要仅运行 `git diff <base>...HEAD` 来代表当前工作区，它会遗漏未提交改动和未跟踪文件。
- **提交**：审查所指定提交相对其父提交的 diff；若是 merge commit，先明确要审查第一父变更还是合并结果。
- **分支/基准点**：验证基准引用可解析，使用 `git diff <base>...<head>` 观察共同祖先之后的改动，并列出对应提交。若用户指定两端比较而不是共同祖先，则按其指定的比较语义执行。
- **PR**：优先读取 PR 描述、评论、目标分支和完整 diff；能通过现有 CLI/API 只读取得时直接查，不因缺少 issue tracker 初始化文件而停止。

若用户只说“review”且工作区存在改动，默认审查当前工作区，并在结论里明确纳入的文件与状态。只有目标确实无法从会话和仓库状态判断时才问一句。基准无效、diff 为空或对象不可访问时，说明阻塞的那一部分；仍可审查其余明确指定的范围。

## 2. 收集判定依据

依次查看用户提供的需求、PR 描述、关联 issue、仓库中的 spec/ADR/README，以及与改动相关的 `AGENTS.md`、`CONTRIBUTING.md`、lint 配置和测试。Issue tracker、特定文件约定或 `/setup-matt-pocock-skills` 都不是前置条件。

找不到需求材料时，继续做代码质量、安全性、回归和仓库规范审查，并把“缺少需求依据”作为覆盖限制；不要把没有证据的推断写成需求缺陷。区分：

1. **需求**：明确需求被遗漏、实现不符，或增加了有风险的未要求行为。
2. **实现与规范**：边界、错误处理、并发、数据迁移、性能、安全性，以及与仓库既有约定不一致之处。

仓库规范优先于通用建议。可参考 [实现异味清单](references/implementation-smells.md)，但这些只是需要上下文支持的判断线索，不是自动违规清单；略过已有工具会确定性检查的问题。

## 3. 检查并验证

先读完整 diff 和必要上下文，再沿调用链检查改动的实际影响。重点覆盖输入校验、权限边界、资源清理、持久化和兼容性。测试只用于验证重要假设或回归风险：优先运行项目已有的窄范围命令；不要因审查而修改代码或安装依赖。无法运行时说明原因和影响。

子 agent、代码图工具或外部检索按可用性和任务规模选择；它们是加速手段，不是必需条件。多个审查者结论冲突时回到源码、需求和测试取证，不要机械拼接报告。

## 4. 报告

分别在 `## 需求` 与 `## 实现与规范` 下列出按严重度排序的可行动发现，每项包含：

- 严重度与简短标题；
- 文件/行号或具体 diff 位置；
- 触发条件和用户可见影响；
- 为什么现有检查没有排除该问题；
- 最小修复方向（无需直接改动）。

仅报告由本次改动引入或明显暴露的问题；不要把猜测、纯风格偏好或未改变的历史缺陷列为确定发现。随后分别说明两轴的发现数量与最高严重度，再说明已检查范围、运行的验证、未覆盖部分，以及是否存在需求材料。没有发现时直说“本次审查范围内未发现可确认问题”，并注明测试或环境限制，不把静态阅读描述成运行验证。
