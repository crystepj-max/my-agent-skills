# 实现异味检查线索

这些重构线索来自 Fowler《Refactoring》的常见类别。它们不是自动违规项：只在本次 diff 提供证据、与当前任务相关且仓库约定没有相反要求时报告。先确认工具没有已经检查该问题，再写出具体 hunk、触发场景和影响。

| 线索 | 观察点 | 可能的改进方向 |
| --- | --- | --- |
| Mysterious Name | 函数、变量或类型名无法说明行为或含义 | 选择明确的领域名；若难以命名，查清设计意图 |
| Duplicated Code | 多处重复相同逻辑或规则 | 找到共同变化原因后提取共享实现 |
| Feature Envy | 方法主要读取或操作另一个对象的数据 | 将行为移到更接近其数据的边界 |
| Data Clumps | 同一组字段或参数总是一起出现 | 判断它们是否构成一个领域概念或参数对象 |
| Primitive Obsession | 字符串/数字承担有约束的领域概念 | 在需要验证和行为时引入小类型或解析边界 |
| Repeated Switches | 多处按相同类型重复条件分支 | 集中映射或使用稳定的多态实现 |
| Shotgun Surgery | 一项逻辑改动迫使散落的多文件同步修改 | 收拢共同变化的行为或更新可发现的抽象边界 |
| Divergent Change | 单个模块因无关原因反复改变 | 按独立职责拆分变化原因 |
| Speculative Generality | 代码为当前需求之外的假想场景增加扩展点 | 在没有证据时简化到当前可验证需求 |
| Message Chains | 调用者依赖过长的对象导航链 | 在稳定边界封装必要的查找或操作 |
| Middle Man | 类型/函数只转发调用而不增加语义 | 删除无意义转发层，或让它承担清晰的边界职责 |
| Refused Bequest | 子类型继承却忽略父类型大部分行为 | 重新评估继承关系，必要时改组合 |

报告异味时说明它为什么在当前变化里带来维护成本；不要只贴标签，也不要把“重构后可能更好”列为确定缺陷。
